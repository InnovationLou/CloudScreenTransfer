# CloudScreenTransfer 0.1 协议

本文描述版本 0.1.0 的实际实现。二进制协议版本为 1，画面头和键盘回执使用 `CST1`，文件元数据使用 `CSTF`。实现见 [protocol.cpp](../src/protocol.cpp)、[frame_codec.cpp](../src/frame_codec.cpp) 和 [file_transfer.cpp](../src/file_transfer.cpp)。

软件在云桌面显示编码画面，物理机抓取云桌面客户端窗口并写入文件。回执通过已有的键盘上行通道发送，不建立 TCP、UDP、HTTP、反向网络连接或文件共享。一次运行处理一个文件；两端不需要预先知道文件内容。

## 固定参数与容量

| 参数 | 0.1 的值 |
| --- | --- |
| 画布客户区 | 1000 × 600 物理像素，必须完整可见、1:1 |
| 数据区 | 从 `(24,84)` 开始，952 × 492 像素 |
| 数据格子 | 2 × 2 像素，4 级亮度 |
| 标称亮度 | 32、96、160、224；按 Gray 标签 `00,01,11,10` 排列 |
| 发送目标 | 5 帧/秒；实际提交和远端更新速度可能更低 |
| 每帧 packet 数 | 114 |
| 每 packet RS 码字 | 255 字节，其中消息 207 字节、校验 48 字节 |
| 每 packet 文件净载荷 | 187 字节 |
| 一个数据窗口 | 256 帧 × 114 块 = 29,184 块 |
| 一个完整数据窗口 | 5,457,408 字节 |
| 一个完整数据帧 | 21,318 字节文件净载荷 |

RS 使用 libcorrect 的 GF(256) 参数：本原多项式 `0x187`，首根 1，根间隔 1，校验长度 48。一个码字可纠正最多 24 个未知字节错误；超出范围后不能保证恢复。RS 成功仍须通过消息 CRC 和身份检查。

114 个码字按字节交织：第 `b` 个字节、第 `s` 个 slot 存放于图像字节流的 `b×114+s` 位置。字节按高位在前拆成四个 2-bit 符号，再映射到灰阶格子。接收端用画面中的四个亮度样本校准，不使用已知文件或随机数据作为解码答案。

仅按数据容量计算，`187×114×5 = 106,590 B/s = 106.59 KB/s`。这不是实测完整文件速度；还要扣除元数据阶段、丢帧、重传、键盘回执等待和磁盘/SHA-256 时间。本文的 KB 为 1000 字节。

## 身份和 64 位范围

`Manifest` 包含文件大小、完整 SHA-256 和单个 UTF-8 文件名。文件大小、packet 索引、数据窗口号和文件偏移均为 64 位。文件大小最多为 `INT64_MAX`，以匹配 Windows 有符号 64 位文件位置 API；实际文件系统、空间和系统限制可能更低。

传输 ID 是稳定的 64-bit FNV-1a 值，按以下字节顺序计算：

1. ASCII 域标识 `CST1ID`，不含末尾 NUL。
2. 完整 SHA-256 的 32 个字节。
3. 文件大小的 8 个小端字节。
4. 文件名的原始 UTF-8 字节，不做大小写折叠或 Unicode 归一化。

FNV-1a 初值为 `14695981039346656037`，每字节先 XOR，再乘 `1099511628211`，按 unsigned 64-bit 模运算；结果为零时改为 1。

相同大小、SHA 和文件名保持相同 ID，便于恢复；同内容但不同文件名，包括不同名的空文件，具有不同 ID。这样旧文件的 `D` 不会正常匹配另一个文件名的新任务。64-bit ID 有碰撞可能，FNV 和 CRC 均不提供身份认证；完整文件内容仍由 SHA-256 验证。回执语义依赖可信的接收端，不用于抵御主动伪造键盘回执。

## 文件元数据

元数据固定为 1496 字节，即 `8×187`。拆为 packet 0 到 7，发送端在独立的公告画面里循环重复这些片段，直到收到 `P` 或空文件的 `D`。元数据不占用数据窗口中的 chunk 数。

所有多字节整数均为小端：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 | ASCII `CSTF` |
| 4 | 2 | 元数据版本，1 |
| 6 | 2 | 固定头长度，80 |
| 8 | 2 | 元数据总长度，1496 |
| 10 / 12 | 各 2 | 画布宽 / 高，1000 / 600 |
| 14 | 2 | 每帧 slot 数，114 |
| 16 / 18 | 各 2 | 码字 / 校验长度，255 / 48 |
| 20 / 22 | 各 2 | 消息 / 净载荷长度，207 / 187 |
| 24 / 26 | 各 2 | 元数据块数 / 窗口帧数，8 / 256 |
| 28 | 8 | 文件大小 |
| 36 | 8 | 稳定传输 ID |
| 44 | 32 | 完整 SHA-256 |
| 76 | 2 | UTF-8 文件名字节数 |
| 78 | 2 | 保留，必须为零 |
| 80 | 变长 | UTF-8 文件名 |
| 文件名之后至 1491 | 变长 | 零填充，必须为零 |
| 1492 | 4 | 对前 1492 字节的 CRC32 |

文件名最多 1020 个 UTF-8 字节，必须是单个组件，不能是路径。0.1 进一步限制为最多 255 个 UTF-16 单位，拒绝非规范 UTF-8、NUL/控制字符、路径分隔符、冒号、尾部空格/句点及 Windows 保留设备名。文件层也保留 `.cst-` 前缀给断点文件。基本命名规则见 [Microsoft 的文件与路径命名说明](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)。

解码必须同时验证整体 CRC、版本、固定配置、保留字段、文件名、大小和传输 ID。通过单个片段 CRC 不代表元数据整体可信。

## Packet 和文件偏移

每个 RS 消息固定为 207 字节：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 8 | 传输 ID |
| 8 | 8 | packet 索引 |
| 16 | 187 | 数据 |
| 203 | 4 | 对前 203 字节的 CRC32 |

索引 0 到 7 是元数据片段。文件数据块 `k` 的 packet 索引为 `8+k`，文件偏移为 `k×187`。最后一块只写入 `min(187,size−offset)` 字节；其余消息字节是填充，不计入文件长度或净载荷。越出文件范围的块不能写入。

全零 `Packet{}` 可供画面填充，接收端拒绝其零传输 ID。发送端也会重复元数据填充小文件的空余 slots。

CRC32 为常见的反射 IEEE CRC32：多项式 `0xEDB88320`，初值与最终 XOR 均为 `0xFFFFFFFF`。二进制 CRC 字段按小端存放。

## 画面头

32-byte 画面头有三份独立拷贝，用黑白 4×4 格子表示。CRC 无效的拷贝可以跳过；如果出现两份内容不同但 CRC 都有效的头，整幅画面头被拒绝，以免把撕裂画面当作一致状态。

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 4 | `CST1` |
| 4 | 1 | 版本，1 |
| 5 | 1 | bit 0 为发送端完成标记，其余位必须为零 |
| 6 / 7 | 各 1 | 校验长度 48 / 数据 cell 大小 2 |
| 8 | 8 | 传输 ID |
| 16 | 4 | 画面提交序号 |
| 20 | 8 | 数据窗口号 |
| 28 | 4 | 对前 28 字节的 CRC32 |

画面提交序号不是文件偏移或 ACK 位号。文件恢复靠 64-bit packet 索引与窗口号，因此 32-bit 画面序号回绕不会截断文件。

每个解出的 packet 必须具有正确 CRC，且传输 ID 必须匹配画面头。文件层再检查当前活动文件和数据窗口。即使画面局部更新混合了多个帧，只有通过这些检查的块才能写入正确文件偏移。

## 数据窗口与回执

数据窗口 `w` 包含数据块 `w×29184` 开始的最多 29,184 块。窗口内帧 `f` 对应 `f×114` 开始的最多 114 个块。位图中某帧的 bit 为 1，表示该帧所需的所有实际文件块都已正确接收；最后一帧不要求填充 slots。

回执正文为 109 个 ASCII 字符，另加 CR，线路长度共 110：

```text
CST1 + op(1) + id(16 hex) + window(16 hex) + mask(64 hex) + crc(8 hex) + CR
```

十六进制与字母以大写生成，接收允许大小写。CRC 按规范化为大写的前 101 个 ASCII 字符计算。mask 是按字节顺序输出的 32-byte 位图；frame 0 是第一个字节的最低位，frame 255 是最后一个字节的最高位。

| 操作 | 含义和约束 |
| --- | --- |
| `M` | 请求重新公告元数据；window=0、mask 全零。协议允许未知 ID=0，GUI 实际只在有效画面头后使用其非零 ID。 |
| `P` | 接收进度；非零 ID，window 为接收端当前数据窗口，mask 描述完整帧。完成前缀窗口也可编码，不能据此认定 SHA 已通过。 |
| `D` | 接收端已完成最终文件并验证 SHA；非零 ID，window=0、mask 全零。 |

流解析器限长，检查结构和 CRC，丢弃损坏/截断命令并寻找下一个 `CST1`。只有完整命令及终止符才交给发送端。

发送端跳过已经 ACK 的帧，轮流补发其余帧。接收端对每个 chunk 去重，乱序数据直接按 64-bit 偏移写入。当前窗口的 `P` 位图可被接收端更新或回滚；正常发送时旧窗口 `P` 被忽略。显式 `M` 重新协商后，首个有效 `P` 可选择接收端真实的恢复前缀，包括新目录的窗口 0。

GUI 回执线程要求云桌面客户端在前台、画布位置有效且最近捕获可用，修饰键未按住。它先点击画布空白位置，再按扫描码逐字发送；每次 key/mouse down 均有 release 路径。110 字符约需 2.2 秒。系统权限或焦点不匹配会使回执等待，不能当作传输成功。

物理接收端初次启动或重新启动时，尚无 manifest 的 `M` 会绑定刚验证的画面头 ID。这个步骤使仍在发送数据的云端能重新公告元数据，而不是让接收端永久等待。

## Checkpoint、续传和完成

接收端只保存一个数据窗口的 chunk 位图，大小 3648 字节，不按文件大小分配内存。SHA 以 64KiB 缓冲区流式计算；源端每个数据帧读取最多 21,318 字节。文件内容保存在磁盘的 `.part` 中。

Checkpoint 文件名包含稳定 ID 和文件名 CRC，内容还保存完整 SHA、大小、原文件名、当前窗口、chunk 位图、状态及整体 CRC。写入流程为刷新 `.part` → 写并刷新新的 checkpoint → 同目录原子替换 checkpoint。完成前缀仅在这一流程后向下一窗口前进。

未完成窗口通常每约 2 秒 checkpoint。`P` 可以反映当前内存中已写入的 chunk；突然退出后该窗口可回退到最后 checkpoint，由新的位图要求重发。不要把每个进度 bit 都理解为一次独立的永久提交。

续传要求相同文件身份和同一个接收目录。已有 checkpoint 必须与完整身份匹配；损坏或不一致时拒绝覆盖。已经完成的文件会重新计算 SHA 后才再次确认完成。

完成顺序是：全部实际数据块接收 → 文件长度正确 → 完整 SHA 与 manifest 相同 → 无覆盖地重命名 `.part` → 保存完成 checkpoint → 接收端允许 `D`。同名目标文件会保留，新输出选择附加编号的名字。重命名过程的中间状态也被记录，恢复时检查实际目标内容。

发送端收到匹配身份的有效 `D` 才进入完成状态；`P`、100% 进度、收到最后一帧或画面头的完成标记都不能替代接收端 SHA 验证。

空文件不进入数据窗口：收到并验证 manifest 后，创建空输出、核对空内容 SHA、提交完成状态，再发送 `D`。1-byte 等小文件同样经过完整检查，只是最后数据帧所需 chunk 更少。

## 计量和范围

物理接收端的速度只累计本次首次正确写入的实际文件字节，排除元数据、RS、CRC、重复块、填充和历史续传数据。最终完成时间还包含协商、等待和 SHA/磁盘操作。发送端 ACK 进度可能直接恢复已有前缀，因此只显示文件进度，不把它当成新传输速率。

0.1 传输单文件的主数据流和文件名，不保存源时间戳、ACL、备用数据流或目录树。固定显示参数不自动适应缩放。没有回执时会继续等待/补发，不会自行宣布成功。64-bit 偏移和离线回归测试也不能代替真实云桌面上的大小文件验收。
