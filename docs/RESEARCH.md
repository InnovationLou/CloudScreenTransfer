# 已测研究记录与 0.1 选择

本文件只整理已经得到的测量事实和当前工程选择，不开展新的图片或音频算法研究。公开项目不包含原始截图、录音、私有路径或个人信息。

研究环境是 Win7 云桌面通过 GDI 显示，经云桌面客户端呈现在物理 Windows 机器上，再从可见画面抓取数据。云端网络隔离；键盘上行可用。速度取决于整条显示链路，不仅取决于本地绘制或截图 FPS。

以下速度均为十进制 KB/s。旧探针统计的是首次通过实际 RS 和 CRC 的合成净载荷，不是收到一个完整用户文件、落盘并通过 SHA-256 的速度。

## 四灰精测

一轮四个 60 秒阶段，统一排除首秒，分母为 59 秒：

| 阶段 | 格子 / 灰阶 | FPS / 纠错字节 | 净载荷 KB/s |
| --- | --- | --- | --- |
| 第一次基线 | 2px / 四灰 | 5 / 64 | 69.0840 |
| 提高提交频率 | 2px / 四灰 | 6 / 64 | 53.0100 |
| 基线复测 | 2px / 四灰 | 5 / 64 | 75.5820 |
| 高容量候选 | 2px / 四灰 | 5 / 48 | 96.2121 |

5 FPS / ECC48 是这轮最佳结果。提高到 6 FPS 没有改善收到的新数据，因此 0.1 不继续推高发送频率。不同阶段的先后历史、显示链路状态和有效更新数都有变化，不能把表中差异全部归因于单个参数。

ECC48 阶段的共同 10 秒级趋势也说明不能把一次平均值称为长期稳定：首个 10 秒约 66.006 KB/s，随后四个完整 10 秒为 103.4094 / 103.4094 / 103.4094 / 105.6096，最后 9 秒约 95.342。完整 59 秒的 96.2121 才是该阶段主指标；只截取较快的后半段会改变问题。

旧 ECC64 的 packet 净载荷为 177 字节，ECC48 为 193 字节。减少校验会增加容量，但不会让没有收到的画面自动恢复。该轮 ECC48 的有效观察能通过真实 RS+CRC，不代表所有未来文件内容或显示状态都具有相同误码裕量。

## 屏幕与音频同时运行

后一次联合测试的共同物理 QPC 窗口为 59 秒：

| 指标 | 结果 |
| --- | --- |
| 共同窗口屏幕新净载荷 | 2,864,699 字节 |
| 共同窗口屏幕速度 | 48.554220 KB/s |
| 音频自动解码的有效净载荷 | 0 字节 / 0 KB/s |
| 联合速度 | 48.554220 KB/s |
| 同一次运行的屏幕单独汇总 | 2,886,701 字节 / 48.9271 KB/s |

两个屏幕数字相差 22,002 字节，恰好是旧 ECC48 探针的一整帧。该帧虽然通过 CRC，解码完成时间却比共同窗口起点早约 57.8ms，因此共同窗口重新计数时排除它。这是窗口边界差异，不是额外丢字节。

这次稳态观察到 132 个不同画面序号，131 个完整恢复，1 个只恢复 23/114 块。该不完整帧少 91 块，仅相当于约 0.298 KB/s 损失。相比之下，观察到的源序号范围内有 159 个序号没有 header 被接收端解出，较少的新画面是主要吞吐损失项。

源时间戳与序号差推算周期约 200.86ms，仍接近 5 FPS。接收端抓屏加解码 p95 约 102.60ms、最大约 137.46ms，没有超过 200ms；抓取约 11.9 次/秒，但新的 header 到达平均约 445.7ms。记录未显示接收 CPU 追不上 5 FPS 的瓶颈。

共同时间窗口内的五个完整 10 秒桶为 46.2042 / 50.6046 / 50.6046 / 48.4044 / 50.6046 KB/s，最后 9 秒约 44.4972。因此较低速度持续于这一运行，而非只有一次启动停顿。

它与前一次 96.2121 的阶段处于不同时间和链路状态，没有紧邻的纯屏幕对照，也缺少这次云端源程序的完整提交统计。不能据此断言“音频使屏幕减半”，也不能精确定位是哪一层限制更新速度。

## 音频结论

此前参考信号中的 PRBS 硬判决分析约有 47% 位错误。后续带同步、训练、RS 和 CRC 的默认 16-QAM 自动解码没有恢复有效包。录音文件大小、48kHz 采样率、理论调制容量都不能计入实际净载荷。

这些结果说明当次实现没有得到可验证的补充数据，不证明所有音频传输方法都不可能。按用户决定，0.1 停止音频分支，完整文件方案只使用图像数据和键盘回执。

## 新完整文件协议

0.1 固定为已有候选参数：2px、四灰、5 FPS、ECC48。每个消息需要 64-bit 身份、64-bit packet 索引和 CRC，文件净载荷为 187 字节：

| 对象 | 每帧净载荷 | 5 FPS 理论上限 |
| --- | --- | --- |
| 旧 ECC48 探针，193B/块 | 22,002B | 110.01 KB/s |
| 新文件协议，187B/块 | 21,318B | 106.59 KB/s |

新协议的可靠性来自明确的文件身份、分块 CRC、RS48、选择性缺帧回执、64-bit 偏移、有限内存窗口、持久 checkpoint，以及最终全文件 SHA。元数据重复公告，使接收端重启后能重新协商恢复位置；空文件和小文件也遵循文件完成验证，而不是只看进度百分比。

发送端先流式计算 SHA，接收端只把实际首次写入的文件字节计为本次新增数据。发送端恢复 ACK 前缀不计作速度展示。这样避免把历史已有文件或源码设定的帧率误报成传输速率。细节见 [协议说明](PROTOCOL.md)。

106.59 KB/s 只是零丢帧时的数据容量。键盘回执约 110 个字符，需要约 2.2 秒；窗口切换、重传、元数据和 SHA/磁盘操作都会占时间。原探针的 96.2121 不能直接当成新程序的完整文件成绩，也不能保证新文件传输超过 100 KB/s。

离线自动测试可以验证二进制格式、真实未知数据的 RS 纠错、掉块/乱序/重复、断点续传、小文件、空文件、同内容不同名、64-bit 边界及最终 SHA。它们不能验证实际 VDI 显示链路和键盘上行的实时表现。

当前需要在用户云环境复测完整程序，以物理接收端的实际新增写入量及最终 SHA 通过为依据；完整文件平均速度使用从开始到确认完成的总时间。本文不以探针峰值、录音大小或模拟测试替代这一验收。
